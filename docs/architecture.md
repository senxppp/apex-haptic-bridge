# 架构与生命周期

## 1. 为什么是"冒充"而不是"接管"

引擎的设备发现是**白名单式**的：它枚举 USB 设备，只对已知 VID/PID 下发使能帧（`0x53`），
之后才建立 `0x57` 实时流。没有使能，就没有任何数据可截。

所以不能"从旁边监听"——必须让它真的认为对端是一台它认识的手柄。
做法是在 USB/IP 上虚拟出这个设备，让引擎正常握手，然后我们成为它的对端。

```
[真手柄 k5]  ✗ 引擎不认 → 静默
[虚拟设备]   ✓ 引擎认   → 0x53 使能 → 0x57 流 → 我们翻译后写给 k5
```

代价是：**引擎看到的是虚拟设备，不是真手柄**。真手柄的输入（按键、扳机行程、陀螺仪）
不经过这条链路，需要人机输入时走系统 XInput，与震动链路互不干扰。

## 2. 进程拓扑

| 进程 | 职责 | 崩了会怎样 |
|---|---|---|
| `usbip_apex6.py` | 虚拟设备 + `0x57` 解析 + 写入节流 | 全链路停（引擎发现设备消失） |
| `k5_writer.py` | 独立进程做 HID 写 | 震动停，但引擎认为设备还在（不触发重发现） |
| `tcp_proxy2.py` | 端口转接 | 设备挂不上 |
| `app.py` | GUI + 编排 + 内联自愈 | 编排能力丢失，链路本身还在 |
| `auto_keepalive.py` | 停帧自愈守护 | 停帧后不会自愈，需要手动重载 |
| `hotplug_reload.py` | 手柄拔插守护 | 拔插后需要手动重载 |
| `watchdog.py` | 引擎进程守护 | 引擎崩溃后不会自动重启 |

写进程单独一个进程是有原因的：`hid` 的写是阻塞调用，一次 20 ms。
放在服务端里会拖慢 `0x57` 的接收——而 `0x57` 是 125 Hz，丢帧就直接掉手感。
隔离之后写进程卡住最多影响震动强度，不影响协议会话。

## 3. 启动时序，以及为什么是"两次挂载"

引擎的发现流程有个固定缺陷：**第一个会话永远不会走快速路径**，它要自己超时一次
（约 60 秒），之后重连才会立刻完成握手。观察到的时序：

```
t=0     起服务端
t=2s    起代理
t=3s    第一次 attach
t=+6s   起探针，等设备稳定 30s
t≈40s   起引擎
t≈40..100s  引擎发现（打印 0x53 使能）→ 但此时还在"慢路径"
t≈100s  detach + attach（重连）
t≈115s  引擎走快速路径，0x57 开始流
t≈115s  验证 stats.log 的 frames 在增长
```

所以 `reload_chain.py` 里的第二次挂载不是"保险"，是**必须的**——不重连，
引擎会一直停在半握状态，`0x57` 一帧都不发。

## 4. 停帧状态机

`frame_guard_core.py` 只做判定，不做动作（便于单测）。输入是两条独立心跳：

- **上游**：音频回环 RMS（有声音说明用户还在放）
- **下游**：`k5_probe.log` 的写入计数（在涨说明硬件还在吃）

```
        ┌──────────── alive ────────────┐
        │  两条心跳任意一条在动就保持     │
        ▼                                │
     stall 被判定                       │
        │                                │
        ├─ 冷却中？ → 只记日志，不动设备  │
        │                                │
        ▼                                │
   quick_cycle()：detach + attach（1.2s）
        │                                │
        ├─ 4s 内 frames 恢复 → alive ────┘
        │
        └─ 未恢复 → 整套重载（~3 分钟），退避 ×2，到上限后放弃并保持可手动触发
```

关键设计：**quick_cycle 不重启引擎**。引擎进程重启要 1 分半，而设备重挂只要 1.2 秒，
且引擎对"同一设备重连"有快速路径。九成的停帧用 1.2 秒就能救回来。
整套重载是最后手段，因为它会打断用户正在进行的会话。

## 5. 关键常量

| 常量 | 值 | 依据 |
|---|---|---|
| `k5_min_iv` | 0.08 s | 写一次 20 ms，留 4 倍余量；12.5 写/s |
| 停帧判定 | 1.0 s | 正常心跳 1 次/s，丢 1 次就算可疑 |
| quick_cycle | 1.2 s | detach 0.2 + 稳定 1.0 |
| 重载阈值 | 4.0 s | 快速重连后引擎约 2 s 内恢复出帧 |
| 热插拔去抖 | 2.0 s | 插拔机械抖动实测 < 1 s |
| 热插拔稳定 | 8.0 s | 设备枚举完成后再动作 |
| 热插拔冷却 | 240 s | 防连续插拔把链路刷爆 |
| 写入超时 | 3 s | 超过就判定 HID 挂起，计数进 stats |

## 6. 数据 vs 控制

两条路径故意分开：

- **数据路径**（高频）：`0x57` → 解析 → 写 HID。全程不落盘、不加锁（除队列），
  失败只计数不重试。
- **控制路径**（低频）：attach/detach、使能帧、扳机状态切换。全部经 `CHAIN_LOCK`
  串行化，避免自愈与 GUI 按钮同时操作设备。

混在一起的后果很具体：曾经让 `trigger_rest()` 走 `k5_force_trigger()`，
那里的 `max(1, p2)` 把 0 抬成 1，回落后的"常态"比开机常态更硬——
用户听到的是"音乐停了扳机还在震"。控制路径的每个字节都必须和开机初始化一致。
